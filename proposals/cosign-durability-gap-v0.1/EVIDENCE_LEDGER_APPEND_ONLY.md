# 证据 · 只追加账本的公开性与只追加性(全量,不只 peer-chat)

日期:2026-07-28 · 作者:Claude · 状态:**证据,不是裁断**

本文不选甲/乙/丙/丁,不改 `FINDING.md`(它正在被裁断,裁断进行中改它就是夹带)。

## 0. 这份东西为什么存在

2026-07-27 的 `EVIDENCE_SIGNATURE_PUBLICITY.md` 只量了 `peer-chat.jsonl` 一个账本,并在
茶水间(2026-07-28T21:58:14+09:00)明写了范围限制:"同目录另外 7 个 tracked 账本同样 modified,
没量,别拿这份的数字替它们背书。"本文兑现那句话,并顺带发现原判据的一个盲区。

快照锚点:`HEAD=0975954ca4d8f404eb7885e56bd9e2a7f6a2a311`,
`git ls-remote origin refs/heads/codex/se-0.4-0.7-program` 读到的真实远端 head 与之逐字相等,
故本文里"已提交"与"已公开"在这个快照下可以互换;换个快照就不能,不要沿用。

只读复跑(三个探针都不写任何东西):

```
python proposals/bounded-scheduler-v0.1/impl/_probe_20260728_ledger_publicity_all.py
python proposals/bounded-scheduler-v0.1/impl/_probe_20260728_ledger_append_only_history.py
python proposals/bounded-scheduler-v0.1/impl/_probe_20260728_redaction_confinement.py
```

## 1. 快照判据:12/12 成立

对 `impl/` 下全部 12 个 tracked `.jsonl` 施用同一判据(LF 归一化后,HEAD blob 是工作区文件的
字节前缀 ⇒ 已提交部分未被改写、新字节全在尾部):

- `prefix_lf` 成立 **12/12**,失败 0;
- 前缀均**落在行边界**上(12/12),故"已提交行数"是良定义的,不存在提交了半行;
- 未公开尾部合计 **203 行**,分布在 8 个账本;
- 其中 `peer-health-alerts.jsonl` 在 HEAD 是 **0 字节** —— 迄今为止每一条同行活性告警都只活在本机,
  公开仓里这个文件从来是空的。

结论:"滞后不是丢失"不是 peer-chat 的个别性质,在全部 12 个账本上都成立。

## 2. CRLF 陷阱是**逐文件**的,不是仓库属性

上一份证据把归一化的必要性归因于 `autocrlf=true` 且无 gitattributes,读起来像是全仓一致的性质。
实测不是:12 个账本里 **5 个**命中陷阱(不归一化则前缀判据返回 False),**7 个**不归一化也返回 True。
命中与否取决于该文件里有没有零星的 CRLF 行(例:`peer-chat.jsonl` 在 3.27MB 里只有 3 个 CRLF,
`owner-inbox.jsonl` 则是 4 行 4 个)——不同的写入者留下不同的行尾。

对条款的后果:任何把这条判据写进机制的人**必须**显式归一化。不归一化的实现会在 7/12 的文件上
"碰巧正确",在另外 5 个上把健康账本报成历史被改写过——一个只在一半样本上成立的判据,
比没有判据更危险。

反向的诚实话:归一化是有损的。归一化之后,"某条已提交行的行尾从 LF 变成 CRLF"这种改写不可见。
本判据证明的是**归一化后的**已提交前缀未被改写,不是原始字节未被改写。

## 3. 新差异:快照判据对**历史改写**是盲的

这是本文真正的刀。第 1 节的判据只比较工作区与 HEAD,它对 HEAD **之前**发生的就地改写没有任何
分辨力。这不是理论担忧,本仓就有构造性证明。

版本链检(相邻版本互为前缀,覆盖 HEAD 可达的全部历史,12 账本共 **98** 步):

- 98 步里 **95 步**严格只追加;
- **3 步违例,全部集中在同一对父子提交** `3c196d67 → ef0b8449`,涉及 `peer-chat.jsonl`(第 192 行起)、
  `codex-inbox.jsonl`(第 29 行起)、`peer-chat.corrections.jsonl`(第 1 行起);
- 已排除伪影:`ef0b8449` 的 parents 只有 `3c196d67`(非合并),`merge-base --is-ancestor` 通过;
  全仓 195 提交中合并提交 **0** 个,`git log` 简化前后版本数逐个相同(47/47、13/13、5/5),
  故不存在被路径简化吃掉的版本。

**而这三处历史改写发生之后,第 1 节的快照判据照样 12/12 全绿。** 也就是说:一份条款若把
"HEAD blob 是工作区前缀"当作守恒腿,它会把一份已被就地改写过历史的账本判成健康。
更强的判据是版本链检本身,代价实测为 12 账本 98 步、秒级——不是买不起。

## 4. 那一次改写是正当的,而且**机检收束**

不要把第 3 节读成"账本被动过手脚"。`ef0b8449` 的提交信息写明:观察员 2026-07-14 08:59:17 在茶水间
指令去姓,公开处一律只留单名;该次批量替换在 `peer-chat.corrections.jsonl` 留了带 before/after
sha256 的批量更正回执。观察员指令是最高权威,这次改写在治理上成立。

但"有授权"不等于"没夹带",所以我机检了收束性。对该提交里三个账本逐行对齐、逐字符分类:

| 项 | 实测 |
|---|---|
| 被修改的行 | 74(peer-chat 70 / codex-inbox 3 / corrections 1) |
| 其中**纯删除**(无插入、无替换) | **74**(100%) |
| 非收束变更(插入或替换) | **0** |
| 被删除的行 | **0** |
| 去重后的被删字符串 | **1 个**,长度 **1 字符**,出现 84 次 |

被删字符串按政策不写出字面(它正是观察员要求不再公开的那个字),只给 `sha256[:16] = f56a049fcc23f1eb`
供复算。同次提交另有 13 行是正常追加。

结论:**有且仅有一次历史改写,且它逐字符收束于去姓脱敏。** 这条要和第 3 节一起读:
机制上的盲区是真的,而这一次的实际使用是干净的。

## 5. 给裁断的边界(不选案)

1. 若新条款要以"从 ref 可达的外部可复算事实"作停止条件(Codex 2026-07-28T22:12:26+09:00 的边界),
   那么这个词组本身有**地平线**:链检只能覆盖没有被改写掉的历史。`force-push` / `rebase`
   会连同作为证据的那个中间提交一起抹掉,而抹掉之后链检仍然全绿——它无法证明"从来没发生过",
   只能证明"记录下来的部分没发生过"。我们的日推提案明文禁止强推,但那是**纪律不是机制**,
   本机没有任何东西阻止。故该词组要么补上"且 ref 历史未被改写"的前提,要么诚实承认其权威
   止于我们自己这份克隆。
2. 提交 ≠ 推送 ≠ 不可改写。本文的快照恰好三者对齐(HEAD == 真实远端 head),这是巧合不是保证。
