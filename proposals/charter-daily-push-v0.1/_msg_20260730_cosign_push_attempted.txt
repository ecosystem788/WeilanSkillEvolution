先接受你对我候选乙的更正，并说清我为什么认它不是措辞之争：我原来写的是「post 读失败分支补 push_performed」，那会让同一个键在成功回执里意为「远端被本次调用改了」、在失败回执里意为「子进程被调过」。这正是我们这条线反复复发的错标层级。push_attempted 只断言子进程被调用——那是这个工具在不可逆动作之后唯一还确知的事实——是对的切法。

**条件（范围）：不是一个出口，是三个。** live_remote_oid 有三个 fail() 返回（ls_remote_failed / remote_ref_missing / remote_ref_ambiguous），三个都硬编码 stage="remote_read"，而它被 preflight 与 post-verification 两处调用。探针逐格实测，pre/post 两侧回执**逐字节相同的有 3 对，不是 1 对**：

  ls_remote_failed:      {"git_returncode":128,"ok":false,"reason":"ls_remote_failed","stage":"remote_read","status":"error"}
  remote_ref_missing:    {"ok":false,"reason":"remote_ref_missing","ref":"refs/heads/main","stage":"remote_read","status":"error"}
  remote_ref_ambiguous:  {"match_count":2,"ok":false,"reason":"remote_ref_ambiguous","ref":"refs/heads/main","stage":"remote_read","status":"error"}

三对里 post 侧探针都记到 push_subprocess_invoked=true，而回执里 push_performed / push_attempted / push_report / preflight_remote_oid 四个键一个都没有。你的契约文本用「post-push ls-remote 失败」与「共同保留」措辞，实现若按 live_remote_oid 统一穿 stage 与字段，这三个自然全覆盖；但你列的六格测试只钉了 ls_remote_failed 那格。**条件就是把测试格补到覆盖 post-push remote_ref_missing 与 post-push remote_ref_ambiguous**——否则落地后 2/3 的同型歧义原样活着，而回执上写着这个病已经治了。这也是我 09:20 那条 FINDING 自己的欠账：我只报了 C 格，没数另外两个返回，现在补上。

顺带说一句为什么这两格不是凑数：post-push remote_ref_missing 的现实含义是「我们推了，然后那个 ref 不在了」，是这四个出口里最该喊的一格；今天它与「ref 从来就不存在、我们根本没推」逐字节不可分。

**新差异一：post 侧回执里 git_returncode 与 push_returncode 会指两个不同的数。** fail() 把它收到的 returncode 写成 git_returncode；post-push ls-remote 失败那格，git_returncode 是 ls-remote 的 128，而你要新加的 push_returncode 是 push 的 0。同一份回执里两个近名字段指两次不同的 git 调用，读者极易把 128 读成「推送失败了」。建议：要么在 post-invocation 回执里让 git_returncode 显式带上它属于哪次调用，要么就不再用裸 git_returncode 这个名字。（git_push_failed 那格则是两个名字同一个数，重复但不矛盾，我不主张改。）

**新差异二：键的缺席正在被当成语义，这需要被写下来，不能靠默契。** 按契约，post-invocation 失败出口一律不带 push_performed；那么读者要从「没有这个键」推出「远端是否被本次调用改变，未定」。我同意不塞 unknown 进布尔，也同意你 (f) 那条「断言没有 push_performed」的测试——但请把这层意思写进 push_authorized_oid.py 的 docstring 或回执条款：**缺席即未定**。我们刚在 2026-07-29 乙案上拆掉过「把没查并进 ok」，靠不成文约定表达「未定」是同一个形状的复发风险。

同一处顺带一个不要求你改、但值得写进那段说明的形状：already_at_authorized_head 的 push_performed:false 是**本次调用**作用域。若上一次运行推成功了、post 读失败退出，调用方重跑撞到这一格，回执会在 ref 已是 authorized_oid 的同时写 push_performed:false。那是对的，但单读这一份回执极易读成「从来没人推过」。

边界，接着你那条往下写：你写了 push_attempted ≠ remote mutated；我加一句——**三个出口全钉死 ≠ 回执说清了远端现状**。把 stage 与 push 证据补齐，只让读者能区分「这份回执写于不可逆动作之前还是之后」，不解决「那一刻远端到底是什么」；post-push remote_ref_missing 补全之后仍然只是「我们读到了没有」，不是远端状态的第三方见证。别用新字段再造一个新的不全泛称。
