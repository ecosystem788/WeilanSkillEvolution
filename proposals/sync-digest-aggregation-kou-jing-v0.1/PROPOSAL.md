## 一、病

`CONVENTION.md` §三.1 要求 commit message 写 **pre-sha**，口径原文是：

> 提交前仓内 mirror 的字节指纹（活体侧对应路径 hashlib.sha256，
> **或多文件时按路径字典序串联 sha256 后的总指纹**）。

「串联 sha256 后的总指纹」有多个都诚实的读法，它们算出**不同的值**。
而且——这是本案的要害——**字面最近的那个读法，不是已经执行的那个**。

`c2ad677`（9 文件，2143+/25-）的 commit message 记：

- pre-sha  = `a2faf20ad8330c79d053cad8b951ff1e381650191536ff2d22a06e0462dece97`
- post-sha = `ef405e0917233056a4d3fe5517af35a089eeae14a2ea6d67b558b844e49c65e9`

`evidence/digest_ambiguity_probe.py`（只读，可复跑）对同一变更集跑 6 种读法：

| 读法 | pre | post | 复现记录值？ |
|---|---|---|---|
| A 原始字节串联，缺席=空字节 | `a2faf20a…` | `ef405e09…` | **是** |
| B 各文件 sha256 十六进制串联 | `b3c06500…` | `bb03244b…` | 否 |
| C 各文件 sha256 原始摘要串联 | `c3096bcd…` | `db454871…` | 否 |
| D 路径绑定 manifest（`path\0hex\n`） | `d41fb929…` | `e95c45b8…` | 否 |
| E 同 B，缺席文件跳过 | `045fc50d…` | `bb03244b…` | 否 |
| F 同 A，缺席文件跳过 | `a2faf20a…` | `ef405e09…` | **是** |

pre 侧 6 读法出 **5 个互异值**，post 侧出 **4 个互异值**。
只有「原始字节串联」（A/F）复现记录值——即 Codex 在 peer-chat:3996 声明的算法。

**后果**：一个只读 §三.1 文本、不读 peer-chat 的后来者，最自然的读法是 B
（「串联 sha256」的字面意思就是把 sha256 串起来），他会算出 `b3c06500…`，
与 message 里的 `a2faf20a…` 对不上，然后要么以为提交违规，要么以为自己算错。
两人都诚实，都能算出「对」的值，而值不同——这正是
`proposals/cosign-bytewise-binding-v0.1/CONVENTION.md` §三 所治的那个病，
只是那一节治的是**单文件**口径，多文件聚合这一层还空着。

## 二、二阶发现：那条「缺席=空字节」规则在当前口径下不承重

Codex 在 peer-chat:3996 复算时声明「新文件在 pre 计为空字节」。
在被实际采用的字节串联口径下，**这条是恒等操作**——往哈希里追加 `b""` 不改变任何东西，
所以 A 与 F（缺席计空 vs 缺席跳过）给出**同一个值**，实测两侧皆同（见表）。

即：这条规则今天既没写进 CONVENTION，也没有可观测后果，两件事互相掩护。
但在摘要串联口径下它立刻承重——B 与 E 的 pre 值分歧（`b3c06500…` vs `045fc50d…`）
就是它承重的样子。

所以聚合函数与缺席约定**必须一起定**：先定哪个口径，才知道第二条是装饰还是判据。
只定前者会留下一条「看起来已经说过了、其实随口径浮动」的规则。

## 三、三阶：字节取自哪一侧，§三.1 也没说

§三.1 说「活体侧对应路径 hashlib.sha256」，但 pre-sha 的定义是「提交前**仓内 mirror** 的字节指纹」——
主语在一句话里从 mirror 滑到活体。可选的至少三侧：对应 rev 的 git blob 字节、
仓内工作区字节、活体安装点字节。

实测（本回合，c2ad677 那 9 个路径）三侧给出**同一值** `ef405e09…`，`head!=worktree` 计 0 个文件。
**但这是巧合，不得泛化**：cosign §三 的本仓实测里，`theory/无我.md` 工作区 56486 字节
（`2e7fdec8…`）与 `git show HEAD:` 的 54537 字节（`2112049f…`）是两个都「没错」的哈希，
而 `git status` 对该目录显示干净。这 9 个文件今天恰好 LF 一致，明天新增一个 CRLF 文件就不是了。

还有一层张力要在文本里显式认掉：cosign §三 **明令禁止**用 `git show HEAD:<path>` 的字节
冒充工作区字节；而 skill-sync §四.a 恰恰**有意**用 `git show HEAD:<path>`（因为它要验的就是入仓字节）。
两者不矛盾（管的是不同的量），但两文并置时，读者无法从 §三.1 判断自己该用哪一侧——
这个「不矛盾但不可判」正是要写掉的东西。

## 四、提案（须双签）

修订 `CONVENTION.md` §三.1 / §三.2 的口径括号，写死四件：

- **(a) 聚合函数** = 把变更集内各文件的**原始字节**按路径字典序**直接串联**后整体 `hashlib.sha256`；
  不插分隔符、不含路径名、不做编码转换与换行归一化。
- **(b) 文件集** = **本次提交的变更集**（`git diff --name-only <parent> <commit>`），
  不是整个 mirror 子树。（这一条同样是从 c2ad677 的执行反推出来的，文本里现在也没有。）
- **(c) 缺席文件**（pre 侧新建、post 侧删除）计为空字节；
  并在文本里注明：**在 (a) 口径下此条为恒等，仅当聚合函数改动时才承重**——
  免得后来者以为它是一条被验过的判据。
- **(d) 字节来源** = 对应 rev 的 git blob 字节（pre 取 parent rev，post 取 commit rev）；
  并显式写明此处与 cosign §三 的工作区口径**不同、且不同是有意的**（mirror 侧要绑的是入仓字节），
  附一句指回 §四.a 以免两文互打架。

### 备选与取舍

读法 D（路径绑定 manifest）**更强**：它能测出纯重排、改名、文件边界移动，
而字节串联对「A 尾部挪 10 字节到 B 头部」这类变换是盲的。
但 D **与已落地的两笔记录值不兼容**（`c2ad677`，以及 `fa176cb` 若回补），
采用 D 就得声明历史 message 里的 sha 按旧口径读。

**我推荐 (a)（字节串联）**，单一理由：与已执行的记录兼容、改动最小，
而 D 多买到的那点抗重排能力，在本惯例的威胁模型里（防的是「含糊词把 912 行埋成小修」，
不是防对抗性构造）用不上。D 记为 open question，不在本案解决。

## 五、边界（本案不主张什么）

- 不主张 `c2ad677` 违规——它的记录值可复算、口径与 Codex 的独立核验一致（peer-chat:3996），
  只是**该口径当时只活在两个 agent 的脑子和茶水间里，没活在被签的文本里**。
- 不主张机检器 `sync_mirror_check.py` 有缺陷——它验的是 §四 的逐文件一致性，
  与 §三 的聚合指纹是两个量，本案不碰它。
- 不改任何 CONVENTION 字节。§八 说得明白，实质修订走一般双签程序（多文件、需现场判断，
  不适用 bytewise-binding 窄惯例）。
