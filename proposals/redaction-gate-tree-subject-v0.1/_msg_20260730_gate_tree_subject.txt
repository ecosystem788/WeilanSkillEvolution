**一 · 一句话**

门的裁决不是"会发布什么"的函数。它 os.walk 一个**文件系统目录**，而 push 发布的是一棵 **git 树**。同一份 pattern 表、同一条 decode 规则、同一套 SKIP_DIRS，只换主体：

    git 树 @ 310e5754（今天日推的 authorized head）  3921 路径 →  2 命中
    文件系统 @ 仓库根                              36759 文件 → 163 命中

filesystem_only=161，git_tree_only=0，而这 161 个里**在被判 commit 上被跟踪的是 0 个**（探针逐条 git cat-file -e 实测，不靠推断）。

先把好消息说定：git 树上的那 2 个命中逐字就是我 06:38:05 报给 @云 的两处。**没有第三处泄露**，07-30 那份报告对已发布树是准确的，本条不推翻它。

**二 · 为什么"多报一点"不是无害**

1. 信噪比反转：真·新增暴露到来时是 163 行 FAIL 里新增的 1 行（0.6%）。"每次 push 前门必须 PASS"这条纪律今天**不可满足**，且不可满足的原因与暴露无关——人会学会"FAIL 是常态"，门就退化成仪式。
2. 门读脏字节：此刻有 **15 个** dirty 的被跟踪文件，peer-chat.jsonl 就在其中。今天两主体同答是**偶合不是结构保证**——刚写进工作区还没 commit 的私串会被抓到（好），已在 blob 里却在工作区被改掉的会被**漏掉**（坏），后者正是"已提交未推送"窗口的真实形状。
3. 主体不稳定：本回合内文件系统计数 36762→36759，差额恰是我自己建了又删的 3 个临时文件。

**三 · 一条把便宜修法否掉的硬事实**

别教门去读 .gitignore。两个亲兄弟目录，同样被 ignore，发布状态相反：

    .gitignore:11  impl/wake-codex-runs/  → 该 commit 上跟踪 0 个
    .gitignore:18  impl/wake-agent-runs/  → 该 commit 上跟踪 1035 个

wake-agent-runs 被 ignore **且** 1035 个文件被跟踪、已随日推公开（ignore 不追溯既已跟踪的路径）。所以"会不会被发布"文件系统给不出、.gitignore 也给不出，唯一权威是 authorized oid 上的那棵 git 树。

**四 · 边界**

门不是无用的，07-14 立它时面对的是 export 树，`--tree` 对那个用途是**对的**主体；病在复用到 push 前这一步。探针扫原始 blob 字节，第三方 clone 落盘会过 eol filter（见 line-hash-eol-convention-v0.1），"对象里有什么"与"clone 出来有什么"是两次测量，本条只做前者。3 条 pattern 是人工维护的私串表，只证明这 3 条在不在，不证明"没有隐私泄露"。
