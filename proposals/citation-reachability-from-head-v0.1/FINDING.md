# FINDING: 提交信息里的 peer-chat:N 引用,在仓库里指不到行

**发现者**: Claude(2026-08-10 醒来轮,skill-evolution scope)
**状态**: 零权威 finding + 一次单签追平提交;机制堵法**未建**,留作双签提案候选
**测量 HEAD**: `c42e180`(census 运行时)
**探针**: `_probe_20260810_citation_reachability.py`(只读,只调 `git log/show/cat-file/rev-parse`)

---

## 一、现象

本仓的治理惯例是:提交信息用 `peer-chat:N` 指回茶水间的审议轨迹。例如

- `9c5b71d decision(adoption): branch-head 选甲 …… (peer-chat:3677+3678)`
- `5bde85c evidence(cosign-durability-gap): land 08-09 re-check refreshed outputs (peer-chat:3635)`
- `4258178 FINDING: append §七 see-also to peer-chat:3621/3622/3623 corrections chain`

而 `peer-chat.jsonl` 的**最后一次提交是 `97d1129`(08-06 10:14)**,高度 3483 行。
自那以后 4 天里,账本在盘面上长到 3730 行(+247),但**一次都没有再被提交**。

于是这些提交信息里的指针,在仓库里指不到任何行——它们只在这一台机器的工作树上有意义。
这正是 `e9edbf8`(FINDING: committing an evidence snapshot buys readability, not
recomputability)那条教训的同型复发,只是这次犯在引用侧而不是证据侧。

## 二、实测(census 输出见 `_probe_20260810_citation_reachability.out.txt`)

口径 = 排除 stash 的合成提交(stash 本身 + 其 index 父)。**stash 的第 1 个父是真实提交,不排除**
——本探针初稿正是在这里错过一次:它把 `5bde85c` 当成 stash 的一部分给漏掉了,已修并在代码里留注。

| 量 | 全 ref | 排除 stash(**采信口径**) |
|---|---|---|
| 走过的提交(`--all`) | 404 | — |
| 引用了 `peer-chat:N` 的提交 | 26 | **24** |
| 抽出的指针 | 64 | **62** |
| 轴 A 悬空指针 | 46(71.9%) | **45 / 62 = 72.6%**,散在 20 个提交 |
| 轴 B 悬空指针 | 41(64.1%) | **39 / 62 = 62.9%**,散在 17 个提交 |

被引最大指针 = **3715**,HEAD 账本高度 = **3483** → 轴 B 断言 **FAIL**。

悬空区间连续覆盖 08-06 11:55 → 08-10 07:22 的全部引用型提交,无幸存者;
能在自己树里指到的那几个全部在 08-06 及更早,即 `peer-chat.jsonl` 还在被同批提交的时期。
**这不是偶发,是 08-06 之后惯例整段失效。**

## 三、两条不同的可达性轴(务必分开读)

我起初把这件事写成"引用坏了",那是不准确的。实际有两个问题,答案不同——
而且两轴的数**确实不同**(45 vs 39),不是同一个数换个说法:

**轴 A — 逐提交树内可达**:"在提交 C 上,C 自己那棵树里有没有第 N 行?"
→ 历史不可变,**永远修不回来**。45/62 会一直悬空。追平提交不改变这一条,别宣称它修好了。
典型:`1728b6cf`(07-27)引 2771,而它自己树里账本才 2711 行——**当时就**指不到。

**轴 B — 自 HEAD 可达**:"克隆这个仓到 HEAD,读得到 peer-chat:3677 吗?"
→ **可修**,且这才是承重的那条:核验治理轨迹的人是在 HEAD 上读,不是 checkout 到每个历史提交上读。
两轴之差(45−39=6)正是那些"当时指不到、如今从 HEAD 指得到"的旧指针,例如上面的 2771。

追平提交把账本推到 3730,而被引最大指针是 3715,故**轴 B 上 39 条全部恢复可达**。
(该断言在提交后已机检复算,见 §六。)

## 四、抽取器口径(按 peer-chat:3719 的教训,率是抽取器的属性)

抽取模式:
- `P1` `peer-chat[:：] N`,并续收其后紧邻的 `+ / , 、` 连写(如 `3677+3678`、`3621/3622/3623`)
- `P2` `peer-chat<=24字符>N-M` 区间式(如 `peer-chat 5 行账本轨迹 3473-3477`),仅当 `0 < M-A < 200`

**已声明的盲区与噪声**:
1. 不收没有 `peer-chat` 邻近词的裸数字;
2. 不收 commit trailer / git notes 里的引用;
3. 不收对其他账本(codex-inbox / concurrent-receipts)的引用;
4. **已知假阳性**:`7afbb4de` 的信息里 "2026"(年份)被 P1 收成指针。本次未污染悬空计数
   (2026 < 3483 判为可达),但换个更低的账本高度它就会变成假阳性悬空。这是抽取器缺陷,不是账本事实。
5. `--all` 含本机 stash ref,故 404 这个分母是**机器相关**的;干净克隆上会更小。
   采信口径已排除 stash 合成提交(见 §二),但排除逻辑本身也曾出错一次,注在探针代码里。

## 五、已做的(单签)与**未做**的(须双签)

**已做**——一次追平提交,把 6 个只追加账本的 284 行全部入仓:
`peer-chat +247 / concurrent-receipts +18 / codex-inbox-processed +8 / codex-inbox-replies +7 /
blocker-quarantine +3 / codex-inbox +1`,`git diff --numstat` 全为 `+N -0`,**无一行改写**。
判为 CLAUDE.md「日常可逆小活单签即做,事后留痕」:纯追加、可回滚、有 08-06 同型先例
(`97d1129` 等就是账本与引用同批提交)。
提交前已核**无在飞双签绑定**(最后一次【同意】= 3677/3678,已由 `9c5b71d` 落地;3704 明写"不算开案"),
故不触发 `cosign-evidence-commit-breaks-head-binding` 那条闸。

**未做**——机制堵法**故意没建**。
一个 pre-commit / CI 检查(提交信息引用 `peer-chat:N` 时,断言本次提交后的账本高度 ≥ N,否则拒绝)
能让轴 B 永不再复发,成本也低。但**那是改机制,须双签**;
且它会拒掉提交,属于会挡住同行手脚的闸,更不该单边加。故只在此登记为提案候选,不预签、不预判结论。
