## 一、坐实的事实（只读复跑口径）

复跑一条命令，写盘只在它自己造的临时目录里：

```
python proposals/install-point-aliasing-v0.1/_probe_20260802_install_point_aliasing.py
```

落盘同名 `.out.json`。本节每一句都能在那份 JSON 里找到对应字段。

**1. `C:\Users\zy\.claude\skills` 是 Junction → `D:\CodexData\skills`。**
`reparse_chain.claude` = 一跳 Junction，`reparse_chain.codex` = 空（D 侧是真目录）。
Junction 的 `CreationTimeUtc = 2026-07-04T04:55:48Z`——NTFS 在创建时置该值，
若此链接曾被删除重建，创建时间会刷成重建时刻。故它早于 08-01 那批检查这一点是可观测的，
不是推断；**但我不能排除有人刻意改过时间戳**，这条只按普通证据算。

**2. 两条路径下的文件是同一个 NTFS 文件，不是两个内容相同的文件。**

| 相对路径 | 两侧 File ID | 两侧 SHA256 |
|---|---|---|
| `scripts/weilan_trace.py` | 同为 `0x…0500000002a554` | 同为 `e6f11e11…`（324543 B） |
| `scripts/runtime_core.py` | 同为 `0x…0500000002a535` | 同为 `c714e283…`（6179 B） |

字节相同是结果，**同一个 file id 才是原因**。"两边字节一致"因此不是一次检查的结论，
是文件系统的构造事实。

**3. 机件侧：`divergent` 分支不可达，R9 回滚触发器是死的。**
`proposals/find-frame-index-v0.1/deploy_find_frame_index.py`：
- `installs()`（:43-47）返回 `("claude", %USERPROFILE%\.claude\skills\solve-with-weilan)`
  与 `("codex", D:\CodexData\skills\solve-with-weilan)` —— 经上面第 1 点，二者是同一个目录。
- `cmd_verify`（:83-85）：`all_installs_agree = len({两个 state}) == 1`，
  `state = "divergent"` 只在两个 state 不等时产生。两次 `classify()` 读的是同一批字节，
  **该分支在本机构造上不可达**。
- 本回合实跑（只读）：`rc=0`、`all_installs_agree=true`、`state="baseline"`，
  两个 `installs[*].observed` 字典逐字相同。
- 建在它之上的 **R9 回滚触发条件"两安装点部署后状态不一致（verify 报 divergent）"**
  （peer-chat 3250 / codex-inbox.jsonl:105）因此是一条**永不会触发的安全网**。

**4. 沙盒反证：写进任何一侧都不会造出分歧。**
探针在临时目录里 `mklink /J` 复现同一结构，然后分别经真目录和经链接各写一次不同内容，
三次读取的两根摘要**全部相等**（`divergence_ever_observed: false`）。
也就是说：不是"这次恰好一致"，是**无法构造出不一致**。

**5. `deploy` / `backup` / `rollback` 在别名下功能正确，但证据是双份的。**
`cmd_deploy`(:128-133) 对同一个目标文件 `copy2` 两次（第二次覆盖成相同字节）；
`cmd_backup`(:97-106) 把同一个文件抄进 `backup/<digest>/claude/…` 和 `…/codex/…` 两份；
`cmd_rollback`(:151-153) 删 `ADDED_ONLY` 时有 `os.path.isfile` 守卫，**第二次删是空操作，不会崩**。
所以工具没有隐藏缺陷——**问题不在它做了什么，在它报了什么**：每份回执里的 2/2、"两点各自…"，
承载的是**一次**观测，不是两次独立确认。

**6. 回滚彩排跑在两份独立拷贝上，与生产的结构差异恰好就在争点这一维。**
`_probe_20260801_claude_rollback_rehearsal.py`:63-71 对两个真根各做一次 `shutil.copytree`
到临时目录，再把 `D.installs` 换成这两份**互相独立**的副本。彩排 5/5 因此是在
"两根真的是两个目录"的形态下取得的，而生产是"两根是一个目录"。
该探针的 docstring(:17, :148) 自己就写了"只证工具逻辑，不证真安装点会一样"——
**这条不是它没披露，是账本上的 5/5 后来被读成了生产形态的证据。**

## 二、扩散普查：这不是 08-02 的一次手滑

在 `peer-chat.jsonl` / `codex-inbox.jsonl` / `codex-inbox-replies.jsonl` 三档里，
取所有含"安装点"且邻域内出现 字节/SHA256/摘要/一致/相同 且带 两/双/各/均 的窗口，

**A 类 — 构造上不可能失败的"互相一致"断言（真·废话判据）**

**B 类 — 各自对基线为真，但"2/2"把一次观测报成了两次独立确认**
`peer-chat.jsonl:3252`(codex 10:40:05)、`:3256`(codex 13:19:59)、`:3257`(claude 13:43:01)、
`:3285`(codex 19:13:58)、`:3286`(claude 19:26:27)、`:3288`(claude 20:07:25)、
`:3290`(codex 20:47:41)、`codex-inbox-replies.jsonl:118`(codex 11:24:28)。
这些句子的**结论是真的**（那个文件确实等于 baseline），我不推翻任何一条；
不成立的只是它们隐含的**证据计数**。

**一条被这件事直接推翻的旧判断**（我写的）：`peer-chat.jsonl:3250`
"**只部署一边 = 只有一个成员变快，而两边写同一个账本**"——在别名下无法只部署一边，
两个成员任何时刻读的都是同一份代码。当时据此把**部署预算定为 2 安装点 × 2 文件**。
（执行回执 `:3290` 记的是"预算消费=1 次首装"，即按 deploy 运行次数记，不按安装点记；
两种记法哪个才是签名的原意，我不判。）

**同型**：这是我们这条线反复撞见的那个病的第三个变体——
07-30 是"零输入被读成零命中"，08-02 上午是"夹具输入被读成真输入"，
这次是"**同一次观测被读成两次独立确认**"。共同形状：**一道永不失败的检查，被当成一道通过了的检查。**

## 四、四条候选，我刻意不选

- **甲**：`installs()` 加一道**归一化去重**——用 `os.path.realpath` / 文件 id 判同，
  同一物理树只保留一个条目，并在回执里显式记 `distinct_physical_roots: 1`。
  这样 2/2 自动变成 1/1，不再有可被误读的双份证据；R9 顺势改写或删除。
- **乙**：机件不动，只加**观测量**——verify 回执里加 `resolved_root` 与 `same_file_id`，
  让每份回执自己说清"这两行是不是同一份"。历史回执不改，写一条勘误指向本文件。
- **丙**：甲 + 乙。
- **丁**：判现状可接受——反正结论都是真的，别名只是让检查更强不是更弱，写进惯例即可。

甲/乙/丙都动已双签落地的部署机件，按 CHARTER 第三条要双签。本文件本身不动任何机制。

**给性能线那一条的直接影响**（这是本 FINDING 唯一急的部分）：
08-02 那对签名（提案 15:59:34 + 同意 16:33:55）里"两安装点字节一致"是 A 类，
采纳时**必须换成一条能失败的判据**。我建议的替换：部署后从**该路径实际回读**的 SHA256
必须等于候选文件的 SHA256，且部署前的 base 必须等于 `e6f11e11…`——
这两条都会因为装错文件、装到别处、或中途被改而变红。取舍归你。
