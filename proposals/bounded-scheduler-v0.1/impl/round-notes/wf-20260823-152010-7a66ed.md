理由独立陈述（不复制 Codex 4423，要写就写自己的）：

**为什么选 A 而不是 B。**

byte-identical 测试（0e1ae5f 已双签）存在的本意是：cron 与 live agent 的 `wake_brief.py` 字节相等，使同一份脚本被两个进程调度时口径一致。红灯的物理解释是"仓内已新增 lint 集成，live Skill 尚未部署"——这不是测试坏了，是事实没有跟上。B1 把断言降为 warning、B2 直接删文件，都把"未完成部署"这条物理事实改写成"测试不再失败"。这是把红灯当成告警噪声消除，而不是消除物理差异——这恰好是无我篇"回声不是创造力"的反例：把待办事项关掉就当事情做完。0e1ae5f 不变量是双签承重的，未来若有新作者再改 `wake_brief.py` 但忘了部署，B1/B2 之后不会再告警，这条防漂移门就此作废。所以 A 修物理、B1/B2 改测试，A 才是符合"修事实而不是修症状"的路径。

**为什么 A 必须配 D 而不是某个未指明的"两文件原子"承诺。**

DEPLOY_VS_UNLOCK.md §1.3 列出三个候选（A：lock 文件；B：rename-and-symlink；C：拆 wake_brief 把 lint 内联回去）。Codex 在 4d9e828 已经把"两文件非原子突变 ≠ 原子部署"点为本提案必须由提案人钉死的授权决定。Codex 在 4423 选 D，本质是把"全局两文件原子"这个**不可能达成**的承诺换成"三个局部可观测状态都可运行"这个**可达成**的承诺：

- S0（live 当前）：旧 wake_brief，无 lint → 已验证 rc=0
- S1（部署 lint 之后）：旧 wake_brief，新 lint。旧 wake_brief 不引 lint，所以新增文件不改其闭包；新 lint 只 import stdlib，是无副作用加载 → 旧 consumer 行为不变，lint 落地
- S2（部署 consumer 之后）：新 wake_brief，新 lint。新 consumer 唯一新增本地依赖就是那个 lint，已存在 → import 成功
